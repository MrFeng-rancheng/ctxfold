# 2026-11-12 · M0 冒烟实验（第一组真数字）

## 想验证什么

管线能不能跑通；在**本机真实代码库**上，四种成本曲线长什么样；量级是否值得继续做。

## 环境与约束

- 语料：Python 标准库 `Lib/http`（真实生产代码），284 个符号级 chunk / 245 个符号
- 任务：50 轮，随机抽符号提问，gold = 自身 + AST 1-hop 依赖（近似）
- **无网络、无 tiktoken** → token 用估算器 `chars/3.5`，已写入 manifest；绝对数有 ±15% 误差，方法间相对比较同基准
- 不调用任何模型（纯离线）
- 运行：`experiments/runs/20261112-193022-m0-http/`

## 看到了什么

| 方法 | 总 token | C_cum | R_prompt（严格） | R_avail（可召回） | 第1轮 token | 第50轮 token | 单轮峰值 |
|---|---|---|---|---|---|---|---|
| full（全量） | 678,597 | 0 | 0.633 | 0.633 | 659 | 25,347 | 25,347 |
| window-5 | 140,123 | 0.794 | 0.618 | 0.618 | 659 | 4,785 | 8,543 |
| **ours** | **31,265** | **0.954** | 0.613 | **0.793** | 1,005 | **26** | 5,557 |
| ours（悲观，占位符全 recall） | 36,194 | 0.947 | — | — | — | — | — |

三条观察：

1. **成本曲线形态变了，不只是变低**。full 从 659 涨到 25,347（38×），ours 从 1,005 掉到 **26**（末轮几乎零成本：全是占位符，直接取用）。这是"有状态"与"重演"的形态差异，不是省钱差异。
2. **严格证据保留只掉 2 个点（0.633→0.613），可召回证据高了 16 个点（0.633→0.793）**。原因：闭包会**主动**带上本轮问题的依赖，而全量基线只包含"历史上被问过的"。
3. **悲观估计几乎没有惩罚**（C 0.954→0.947）：占位符机制省下的空间远大于 recall 回来的成本。这一条是本方法能成立的关键前提，第一次得到数据支持。

## 哪里不对 / 哪里在骗自己

- **R_prompt 的 0.613 就是漏洞**：38.7% 的 gold 被预算（1600 token）挤掉了。这是 M1 的首要优化目标（预算感知的闭包选择：小依赖优先、可合并的合并）。
- **随机任务序列低估了 window 的损失**。window-5 的 R 只比 full 低 1.5 个点，因为随机提问导致"老证据"很少被再次需要。真实会话有**时间局部性**（同一批文件反复被问），window 会掉得更狠。→ **下一轮必须换"局部性任务序列"**，否则我们等于在给对手放水，论文里会被抓。
- **K=0.14 不是 H**。离线没有任何模型调用，K 只是"全部依赖已固化"的回合比例，仅作代理指标；真正的 H 要在线跑。
- 语料只有 284 chunk，规模太小，不能据此谈泛化。
- gold 用 AST 1-hop 近似，真实"回答所需证据"通常还要更宽（跨文件、配置、测试），所以 R 的绝对值整体偏高估。

## 下一步（按优先级）

1. **任务序列生成器升级**：加时间局部性（70% 提问落在最近 8 轮用过的文件上），并加"跨文件依赖"任务。这是让对比变公平的前提。
2. **预算感知的闭包选择**：按 token/信息比排序，允许丢大依赖但标"需 recall"；目标 R_prompt ≥ 0.75。
3. **接 tiktoken**（有网后）+ 用真实语料校准估算器。
4. 引入「世界指纹」实验：模拟文件被改，看 stale 传播与重算量。

## 一句话结论（第一轮）

管线通了，量级成立（C≈0.95，R_avail +16pt），且**机制假设第一次有了数据**；但当前对比对 window 太宽容，下一轮必须先修公平性再谈结论。

# 同日第二轮：公平性修正与对抗场景

## 1. 我的预测错了，而且错得有用

我原本判断："真实会话有时间局部性（反复问同一批文件），所以 window 会掉得很惨。"
**实测相反：局部性反而帮了 window。**

| 任务序列 | window R_prompt | full R_prompt |
|---|---|---|
| 随机（第一轮） | 0.547 | 0.600 |
| 时间局部性 | 0.632（↑） | 0.673（↑） |

原因：局部性使"最近 5 轮"恰好覆盖当前要用的文件，窗口法正中靶心。
**结论：时间局部性不是压力测试，是 window 的主场。**

## 2. 真正的对抗场景：长程引用

构造方式：40% 的任务问"新符号 A 怎么和 8~45 轮前那个符号 B 配合"，gold = {A, B} ∪ deps(A)。
此时窗口法必须失败——B 早已滑出窗口。

| 方法 | 总 token | C_cum | R_prompt | R_avail | 末轮 token |
|---|---|---|---|---|---|
| full | 340,790 | 0 | **0.719** | 0.719 | 14,010 |
| window-5 | 71,426 | 0.790 | 0.573 | 0.573 | — |
| **ours** | **19,469** | **0.943** | 0.498 | **0.871** | **47** |

诚实读法：**严格指标上我们输了**（0.498 < 0.573 < 0.719），可召回指标上我们最高，成本 5.7%。

为什么严格 R 反而更低？因为 gold 里有 **38.7% 是"已固化"的老结论**——它们按设计以占位符出现，不算"原文在 prompt 里"。所以：

> **R_prompt 与 R_avail 是两种不同的东西。我们卖的是后者；前者是"模型从不 recall"的最坏情况。**

这一条必须写进论文，并作为核心风险：**如果模型不会主动 recall，我们的优势就是纸面的。** → M1 必须有在线实验证明"模型会用 recall"。

## 3. 预算不是瓶颈（一次证伪）

| budget | 600 | 1200 | 1600 | 2400 | 3600 |
|---|---|---|---|---|---|
| R_prompt | 0.471 | 0.507 | 0.498 | 0.508 | 0.528 |
| R_avail | 0.777 | 0.829 | 0.841 | 0.851 | 0.871 |
| C_cum | 0.952 | 0.943 | 0.943 | 0.940 | 0.932 |

预算放大 6 倍，严格 R 只涨 2 个点。**说明优化方向不应是"装更多"，而是"改装配策略"。**

## 4. 修掉一个设计漏洞（数据驱动）

诊断发现 gold 分解：原文 46.2% / 占位符 33.6% / **彻底缺失 20.2%**。
缺失的根因：超预算的依赖被**直接丢弃**，连"可 recall"都没留。

改为"未加载占位符"（只列 id + 名字，成本≈几 token）后：

| | 修复前 | 修复后 |
|---|---|---|
| 彻底缺失 | 20.2% | **15.1%** |
| 可召回 | 33.6% | 38.7% |
| R_avail | 0.841 | **0.871** |

剩余 15.1% 的缺失来自：2-hop 依赖未展开、同名符号解析失败。→ 下轮处理（`--hops` 已加进 assembler，但实验脚本尚未接线）。

## 5. 下一步（按优先级）

1. **接线 hops=2** 并测它对缺失率与成本的影响（可能得不偿失，要用数据说话）。
2. **在线小实验（最高优先）**：拿 30 条 far_ref 任务，用最便宜的模型 API 跑，测"模型是否真的调用 recall"→ 得到真实的 H 与端到端 A。**没有这一步，R_avail 的优势无法辩护。**
3. 世界指纹实验：模拟文件被改，量化 stale 传播与重算量（这是"防错体系"的第一块数据）。
4. 接 tiktoken 校准。

## 6. 本轮实验目录

- `20261112-193110-m0-http-rnd`（随机序列）
- `20261112-193110-m0-http-loc`（局部性序列）
- `20261112-193125-...-b600/1200/1600/2400/3600`（预算扫描）
- `20261112-193214-...-h1`（未加载占位符修复后，hops=1）

# 同日第三轮：世界指纹实验（防错体系的第一块数据）

## 1. 实验设计

把语料复制成可写仓库 → 跑 12 轮建记忆（23 条）→ 在真实文件里插入注释行（AST 仍合法）模拟"代码被改" → 分别按 **文件级 guard** 与 **符号级 guard** 判定失效。

## 2. 结果（主设置：改 3 个符号，落在 3 个文件）

| guard | 失效条数 | 需重读 token |
|---|---|---|
| file（文件哈希） | **21** | 8,933 |
| symbol（符号哈希） | **3** | 537 |

- 误失效 **18 条 = 记忆总量的 78.3%**
- 重算成本比 **16.6×**

## 3. 敏感度（真实修改 1/3/6 个符号 × 2 个种子）

| 设置 | file 失效 | symbol 失效 | 误失效 |
|---|---|---|---|
| 1 个符号 / seed 7 | 11 | 1 | 10 |
| 1 个符号 / seed 13 | 2 | 1 | 1 |
| 3 / seed 7 | 21 | 3 | 18 |
| 3 / seed 13 | 17 | 3 | 14 |
| 6 / seed 7 | 23 | 5 | 18 |
| 6 / seed 13 | 22 | 4 | 18 |

**诚实解读**：符号级 guard 的失效集合**永远 ⊆ 文件级**，这是结构性的；但"省了多少"高度依赖文件的大小分布——改动落在大文件里时差距 10~18 条，落在小文件里只差 1 条。所以论文里不能写"16 倍"，要写"坏情况 16 倍、中位约 10 条误失效、下限 0"。

补充：symbol 失效数有时少于修改数（6 改 5 失效），因为被改的符号未必在记忆里——这是正确行为，不是漏检。

## 4. 一个负面结果：2-hop 闭包不值得

| | hops=1 | hops=2 |
|---|---|---|
| ours 总 token | 19,469 | 21,466（+10%） |
| R_prompt | 0.498 | **0.407（↓）** |
| R_avail | 0.871 | 0.871（不变） |
| K | 0.220 | 0.320 |

2-hop 只是把更多 chunk 塞进有限预算，导致"该给原文的项"被挤成占位符 → 严格 R 反而降，可召回 R 不变，成本涨 10%。
**结论：v0.1 默认 hops=1。**（这条负结果要写进论文的消融）

## 5. 由数据引出的指标问题（重要）

R_prompt 会**系统性惩罚好行为**：我们越成功地把已知证据固化为占位符，R_prompt 就越低——尽管信息一点没丢。
→ 需要一个新指标进入 protocol.md：
**R_eff = 证据"可被本轮利用"的比例，计入 recall 成本**，即
`R_eff = |gold ∩ (prompt ∪ recallable)|`，同时报 `cost(R_eff) = prompt_tokens + recall_tokens`。
这张"R_eff vs 总成本"的曲线才是本方法真正的卖点图。

## 6. 下一步

1. 把 `R_eff` 写进 protocol.md（预注册，需在跑主实验前定稿）  ← 已完成
2. stale 传播实验：`used_by` 下游污染 + 只重算受影响子图的收益
3. **在线实验（仍是最关键的一步）**：模型到底会不会 recall

# 同日第四轮：账本 / 抽检 落地 + 传播实验

## 1. 落地的两块 v0.1 骨架

- `src/ctxfold/ledger.py`：append-only JSONL 账本。事件类型 commit/stale/suspect/revive/reuse/recall/audit。
  支持 `replay(up_to)` 还原任意时刻状态、`rollback_to(seq)` 截断回退（自动备份原文件）。
- `src/ctxfold/audit.py`：确定性抽检（hash(cid+salt)，可复现），记录 verdict，算 E（错误残留率），
  超阈值触发信任降级建议。无抽检时 E 返回 `None`，**不谎报 0**。
- `tests/test_core.py`：9 条断言覆盖切块/账本回放回退/抽检确定性/占位符免算/file-vs-symbol guard。全部通过。

## 2. 传播实验（离线，200 次随机试验）

记忆 62 条，used_by 边 43 条，有下游的节点 32 个；**全量失效重算成本 23,571 token**。

| 失效几个(k) | 下游污染(均值) | 传播式重算成本 | 相对全量节省 | 传播/仅直接 |
|---|---|---|---|---|
| 1 | 0.85 | 1,092 | **95.4%** | 3.35× |
| 2 | 1.74 | 2,125 | 91.0% | 2.61× |
| 3 | 2.41 | 2,846 | **87.9%** | 3.05× |

读法：一条结论失效时，只重算「它 + 它的下游」比推翻整个记忆省 95%；即使同时坏 3 条仍省 88%。

**必须同时说的诚实边界**：污染闭包之所以小，是因为依赖图稀疏（1-hop、每节点只取 top-3 调用名）。
真实工程的跨文件依赖会更密，传播成本必然上升。另外**传播精度离线测不了**——"疑似污染"里有多少真的需要重算，取决于语义，
只能靠在线抽检的 E 回答。这一轮只给了成本结构，没给精度。这是本实验的局限，论文里必须写明。

## 3. 下一步

1. **在线实验（第三次提及，仍是最关键）**：模型是否真的 recall → 决定 R_eff 优势成立与否
2. 依赖图加密（跨文件 import 边）后重跑传播，看成本上限
3. v0.1 收口：CLI 入口 + 一键复现脚本 + README 数字回填

# 同日第六轮：对照组补齐 —— 我们输了一个指标

## 1. 做了什么

- `src/ctxfold/retrieve.py`：BM25（纯词法，无向量）
- `src/ctxfold/tasks.py`：任务生成独立成模块（可被两个实验复用）
- `experiments/m2_baselines.py`：五方法同台（full / window / summary / grep-RAG / ctxfold）
- 跨文件依赖：`collect_imports` + `module_file_map` + 解析优先级（同文件 > 同包 > import > 全局名）
- 顺带修掉一个隐性偏置：依赖解析原来按**字母序**取 top-3（`sorted(c.calls)`），对以 a/b 开头的符号不公平；改为按源码出现顺序（`call_order`）

## 2. 五方法对比（50 轮，局部性 + 40% 长程引用）

| 方法 | 总 token | 含全量 recall | C_cum | R_prompt | R_avail | 长程引用 R |
|---|---|---|---|---|---|---|
| full | 340,790 | 340,790 | 0 | 0.719 | 0.719 | 0.793 |
| window-5 | 71,426 | 71,426 | 0.790 | 0.573 | 0.573 | 0.355 |
| summary | 43,969 | 43,969 | 0.871 | 0.569 | 0.569 | 0.341 |
| grep-RAG | 40,598 | 40,598 | 0.881 | **0.635** | 0.635 | **0.631** |
| **ctxfold** | **19,859** | 38,260 | **0.942** | 0.514 | **0.878** | 0.306 |

## 3. 必须承认的三件事

1. **严格 R 上我们输给 grep-RAG**（0.514 vs 0.635）。原因不是实现差，是设计：我们把已知证据换成了占位符，而 BM25 每次都把原文重新捞出来。**这是"省钱"与"当场可见"的取舍，不是 bug。**
2. **长程引用场景 grep-RAG 大幅领先**（0.631 vs 0.306）。原因很朴素：**BM25 直接在全库检索，它不需要"记住"**。"长程记忆"这件事，RAG 本身就是一种解，而且很便宜。这直接打击了我一开始对"有状态记忆"的叙事。
3. **等成本下我们确实赢**：全量 recall 38,260 ≈ grep-RAG 40,598，可召回证据率 0.878 vs 0.635（+24pt）。

## 4. 由此改写的论文主张（重要）

原来的主张是"我们证据更全" → **站不住**。
改成：**"在相同成本下，把'证据是否可得'从概率性检索变成确定性闭包；且已知证据的重复开销降为零。"**
grep-RAG 的问题不是覆盖低，而是：① 每次都要重新捞原文（成本恒定不降）；② 检索失败就彻底没有；③ 没有增量性（改一个函数，它不知道哪些结论失效）。

这三条才是我们的差异化，而不是"R 更高"。

## 5. 下一步

1. 给 grep-RAG 做"等精度"切片：把它的预算涨到 R_avail 达到 0.878，看要花多少 token —— 这是协议 §3 要求的另一半对照
2. 在线实验（A/H/E）仍缺
3. 长程引用需要专门机制：现在的闭包只能靠"queried 名字"命中老符号；对"隐含引用"完全无能 → 这是 v0.2 的真课题

# 同日第七轮：等精度切片 —— grep-RAG 撞到天花板

## 1. 结果

ctxfold（全量 recall）证据率 0.878，成本 38,260 token。

| grep-RAG 预算 | 总 token | R_avail |
|---|---|---|
| 1,600 | 42,358 | 0.646 |
| 3,200 | 73,344 | 0.666 |
| 6,400 | 188,131 | 0.677 |
| 12,800 | 361,031 | 0.677 |
| 19,200 | 407,759 | **0.677（封顶）** |

**预算放大 12 倍、成本 10 倍，证据率停在 0.677，追不上 0.878。**

归因：gold 里含 AST 依赖项，而依赖项与 query 往往**没有任何词面重叠**——词法检索在原理上就够不着。
这不是调参能修的，是检索范式的边界。

## 2. 但这个结果有自证风险，必须写明

gold 是 AST 依赖图生成的，而 ctxfold 用的就是同一张图。
→ **"grep-RAG 追不上"部分是指标定义决定的**，属于循环论证，不能当独立证据。
已写进 README 与 RESULTS.md，明确标注"真正的裁决只能来自在线实验（模型答对率）"。

这一条如果不写，审稿人第一轮就会问："你的 gold 是不是照着你自己的图做的？"

## 3. 顺手修掉一个语义 bug

`BM25.top_k` 里预算不足时原来是 `continue`（跳过装不下的、去挑更小的碎片），这会系统性偏向"短小无关片段"。
改为 `break`（预算耗尽即停止）。修完后 grep-RAG 在 k=8 与 k=64 下结果一致（39,399），E1 与 E4 的数字口径才统一。

## 4. 现在的证据格局

| 主张 | 证据强度 |
|---|---|
| 成本可降一个数量级 | 强（多组实验一致） |
| 改一处只重算受影响子图（省 88-95%） | 强（成本结构） |
| 符号级 guard 优于文件级 | 强（结构性 ⊆ + 敏感度扫描） |
| 同等成本下证据覆盖更高 | 中（等成本切片成立，但 gold 有自证风险） |
| 模型会真的 recall | **无证据（在线实验缺失）** |
| 端到端正确率不降 | **无证据** |

# 同日第八轮：在线装置 + 论文骨架

## 1. 在线实验装置（`experiments/m3_online.py` + `src/ctxfold/llm.py`）

- 零依赖 HTTP 客户端（urllib），任何 OpenAI 兼容端点：`CTXFOLD_BASE_URL / CTXFOLD_API_KEY / CTXFOLD_MODEL`
- 支持 **function calling**：模型可主动 `recall(id)` 取回占位符对应的逐字原文 —— 这是"模型会不会 recall"这个问题的直接测量装置
- 任务设计**答案可离线校验**（不需要 judge 模型）：
  - Q1 定位：「符号 X 定义在哪个文件、哪些行」→ 校验 `文件:起-止`
  - Q2 依赖：「符号 X 直接调用了哪些函数」→ 校验集合相等
- 无凭据时**干净退出并打印配置方法**，绝不伪造结果（已验证）

## 2. mock 敏感性推演（明确标注：非实验数据）

假设"有证据时答对率 q=0.85"，扫 recall 概率 p：

| p | A | tokens |
|---|---|---|
| 0.0 | 0.317 | 24,030 |
| 0.5 | 0.511 | 33,376 |
| 1.0 | **0.683** | 35,900 |

两个结论：
1. **A 对 recall 概率高度敏感**（0.317→0.683，翻倍）。这就是为什么 R_avail 的优势必须由在线实验兑现，否则是纸面数字。
2. **即使 p=1.0，A 也只有 0.683** —— 因为有约 20% 的问题在装配后**连可 recall 的证据都不存在**（对应之前测到的"彻底缺失 15%"）。**这是比 recall 率更严重的问题：模型再听话也答不对。**

## 3. 论文骨架落地（`docs/paper-draft.md`）

含：形式化（状态 S=⟨C,G,D,L⟩、guard 可判定性、装配不变量、增量求值）、方法、指标表、
E1–E5 全部真实数字、**§8 效度威胁与负面结果（7 条，含 gold 循环性、严格指标劣势）**、相关工作对位、待补实验清单。

摘要里写的是"降至 5.8%"而不是"省 94%"——因为 5.8% 更接近读者会去核的算法（19,859/340,790）。

## 4. 本轮最重要的一句话

**"彻底缺失 15–20%" 比 "模型不会 recall" 更致命。**
前者是系统缺陷（闭包/预算/解析失败），后者是模型行为。修前者在自己手里，修后者要看别人。
→ 下一轮优先级：把缺失率压下去（诊断具体来源：2-hop？同名解析？预算丢弃？）

# 同日第九轮：诊断 20% 缺失 —— 找出两个会让所有实验数字失真的 bug

## 1. 病因一：同名符号遮蔽（13.7%）

`Lib/http` 上 240~284 个 chunk 里，`__init__` / `__repr__` / `read` / `close` 大量重名；
原索引 `name -> 单个 cid`（先到先得），导致 **13.7% 的符号在检索时被指到别人身上**，
闭包自然拿不到真正需要的证据。

修复：
1. 方法改用**限定名** `Class.method`（遍历时带类前缀）→ 240 个 chunk 名字全唯一，重复组 0；
2. 索引改为 `name -> 所有 cid`，同时收录限定名；
3. 查询里出现限定名时以它为唯一首选；裸名只作**歧义候选**（占位符，不进原文）。

## 2. 病因二：类整块与嵌套函数重复计数（成本虚高 46%）

原来既切「类整块」又切「类内方法」还切「嵌套函数」，同一段源码被算进多个块。
后果：full 基线 340,790 → 修正后 271,982，**所有方法的 token 都被系统性高估**。

修复：只切叶子（模块级函数 + 类内方法），不切类整块、不切嵌套函数。

## 3. 三个版本的同一张表（看清修复的影响）

| | 修复前(1) | 限定名后(2) | 限定名+歧义降级(3) | 只切叶子(4=最终) |
|---|---|---|---|---|
| R_avail | 0.878 | 0.959 | 0.959 | **1.000** |
| R_prompt | 0.514 | 0.443 | 0.418 | 0.623 |
| 成本(不 recall) | 19,859 | 52,909 | 52,588 | **20,574** |
| full 基线 | 340,790 | 498,669 | 498,669 | 271,982 |

(3) 说明：歧义候选塞原文会把成本干到 2.7 倍——**歧义要用占位符解决，不是堆原文**。
(4) 说明：去掉重复计数后成本回到 2 万级，同时 R_avail 达到 1.000。

## 4. 最终五方法表（本轮修正后）

| 方法 | 总 token | R_prompt | R_avail | 长程引用 R |
|---|---|---|---|---|
| full | 271,982 | 0.717 | 0.717 | 0.751 |
| window-5 | 57,572 | 0.578 | 0.578 | 0.376 |
| summary | 43,583 | 0.561 | 0.561 | 0.376 |
| grep-RAG | 43,528 | **0.702** | 0.702 | **0.731** |
| ctxfold | **20,574**（全量 recall 53,234） | 0.623 | **1.000** | 0.449 |

mock 推演（q=0.85）：p=0 → A 0.428；p=1 → A **0.850**（等于上限，说明"缺失证据"问题已消除）。

## 5. 最该记住的一条（方法论）

**前八轮的数字全部带偏差**：13.7% 的检索指错 + 46% 的成本重复计数。
它们不影响"方向"，但影响"量级"，而论文里被引用的是量级。

→ 教训：**指标管线本身必须先被验证，再拿去验证方法。** 已在流程里加了一条：
任何新实验前，先跑 `tests/test_core.py` + 检查 chunk 总数/唯一名数是否合理。

# 同日第十轮：长程引用的真相 + 摘要卡

## 1. 先分清是"没命中"还是"降级"

诊断 far_ref 任务（17 个）的 gold 归属：

| 角色 | raw | placeholder | MISSING |
|---|---|---|---|
| own | 41 | 9 | 0 |
| **old（40 轮前那个）** | **0** | **17** | **0** |

结论：**长程引用的"丢失"100% 是设计性降级，不是检索失败。**
老符号被正确命中、正确固化，所以它以占位符出现——严格指标 R_prompt 必然低。
这不是 bug，是"不重复发送已知内容"的必然代价。

## 2. 于是改进方向不是"修检索"，而是"让占位符更有用"

**摘要卡**：本轮被点名且已固化的符号，内联成一行
`#id | path:start-end | 签名首行 | calls: a,b,c`（约 20–40 token），细节仍可 recall。

效果（模拟推演，q=0.85）：

| | p=0（从不 recall） | 成本 |
|---|---|---|
| 只有占位符 | A **0.428** | 19,652 |
| 加摘要卡 | A **0.867** | 22,114（+7% 总成本） |

**诚实边界**：卡片能直接回答"在哪一行""调用了谁"这类问题；
语义类问题（"这里为什么会死循环"）卡片无能为力，仍需 recall。
任务集恰好偏向前两类，所以这个数字不能直接当"端到端正确率"宣传。

## 3. 顺手修掉依赖解析的同名撞车

`resolve_dependencies` 在多个同名候选里取"全局第一个"，导致 `__init__` 抓到别的类。
改为 **同文件 > 同类前缀 > 全局首个**。依赖边 235 条（跨文件 13 条），成本变化 +7%（卡片）+ 噪声。

## 4. 本轮最终数字

| 方法 | 总 token | R_prompt | R_avail | 长程引用 R |
|---|---|---|---|---|
| full | 271,982 | 0.717 | 0.717 | 0.751 |
| grep-RAG | 43,528 | **0.702** | 0.702 | **0.731** |
| ctxfold | **22,114**（全量 recall 54,795） | 0.626 | **1.000** | 0.429 |

## 5. 下一轮的判断

长程引用在 R_prompt 上注定输（设计使然），继续优化它是**和自己的定义作战**。
更值得做的是把"卡片能答 / 必须 recall"这两类问题**分开测**——
即给在线实验加第三类语义题（"这段代码在什么情况下会失败"），答案用规则校验。
这样 A 才是分层的，而不是被题型结构决定的一个混合数。

# 同日第十一轮：按题型分层 —— 收益其实不均匀

## 1. 加了第三类题：语义题

Q3：「符号 X 会抛出哪些异常类型」→ gold 由源码 `raise` 行解析，规则校验，不需要 judge 模型。
这类题**卡片答不了**（卡里只有签名和调用名），必须读正文或 recall —— 正好用来检验收益的边界。

## 2. 分层结果（模拟推演，非真实数据）

| recall 概率 p | 总 A | 定位类 | 依赖类 | **语义类** | 总 token |
|---|---|---|---|---|---|
| 0.0 | 0.589 | 0.878 | 0.889 | **0.000** | 22,557 |
| 0.5 | 0.719 | 0.822 | 0.867 | 0.467 | 29,052 |
| 1.0 | 0.878 | 0.911 | 0.833 | 0.889 | 35,083 |

**这是全文最重要的分层结论**：卡片把便宜问题（定位/依赖）变成"不 recall 也能答"，约 0.88；
贵问题（语义）在 p=0 时是 **0**。

→ 所以"端到端 A"这个数字毫无意义，除非同时给题型构成。**任何用题型比例调节结论的做法都是作弊，包括我们自己。**

## 3. 顺手修掉一句会惹祸的自动生成文案

`reproduce.py` 原来自动写「在**等成本**下，可召回证据率 1.000 vs 0.702」——
但 54,795 比 grep-RAG 的 43,528 **高 26%**，根本不是等成本。
改成三句都说的版本：

1. 不 recall：22,114（为 grep-RAG 的 51%），严格可见 0.626 vs 0.702（略低）
2. 全 recall（最坏）：54,795（比 grep-RAG 高 26%），可召回 1.000 vs 0.702
3. 卖点不是"同等成本下证据更多"，而是**可召回率接近饱和 + 已知内容不重复付费**

这类"自动生成文案里藏着的过度声明"是最危险的一类错误：它不会报错，只会一直挂在那里被人引用。

## 4. 现在的自我评估（更新）

| 主张 | 状态 |
|---|---|
| 成本可降至 1/8（相对全量） | ✅ 强 |
| 已知内容不重复付费（机制） | ✅ 强，可复现 |

# 同日第十三轮：世界指纹（补上最后一块"文档里写了代码里没有"的机制）

## 1. 做了什么

`src/ctxfold/world.py`：
- `cheap_fingerprint`：(路径, 大小, mtime_ns) 哈希，不读内容
- `content_fingerprint`：逐文件 sha256
- `git_head`：直接读 `.git/HEAD`，不调 subprocess

Runtime 接入：每轮先过 cheap 门；未变则跳过全库重读，变了才 `load()`。
**门只用于"跳过"，不参与失效判定**——误报代价是"多读一次盘"，漏报代价是"用了错的结论"。

自测新增 `test_world`：无变化稳定 / touch 时 cheap 误报而 content 不报 / 内容真变两者都报。**10 条自测全绿。**

## 2. 两个实测数字

| 语料 | 文件数 | cheap | content | 每轮省 |
|---|---|---|---|---|
| Lib/http | 5 | 1.1ms | 2.2ms | 1.1ms |
| 整个 Lib | **2213** | **261ms** | 447ms | 185ms |

## 3. 一个必须承认的负面结果

**2213 文件时，指纹本身每轮 261ms，比装配开销（~1ms）高两个数量级。**

也就是说：如果每轮都校验世界，这套东西会**比不校验慢 200 倍**。

处理方式：加 `gate_interval` 节流（默认 1，大仓库建议 5–10）。
代价是**存在最多 N 轮的失效窗口**——这是安全性上的真实让步，已写进论文 §8 威胁第 8 条。

（顺带记一条：`copytree` 后首次测量会把冷缓存算进去，得到 91× 的假差距；
加预热后才是 2×。**基准测试不加预热，等于自欺欺人。**）

# 同日第十四轮：抽检接进运行时 —— 然后发现它没想象中有用

## 1. 背景

本地没有 Ollama / llama.cpp，环境里也没有任何相关 API key（只有无关的 VIPSHOME），
所以真实 A/H/E 依然拿不到。转而把「抽检」接进 `Runtime.ask`，让它补节流门的失效窗口。

## 2. 实现（真能抓到漂移）

- `Runtime._verify_one(cid)`：只读**那一个文件**、重切、比对符号哈希。
  刻意不依赖 `self.by_cid`——那可能是节流门跳过后留下的旧快照。
- `Runtime.audit_sample(rate)`：按 `hash(cid+salt)` 抽样，判 pass/fail，fail 即标 stale 并记账。
- 实测：改掉一个函数后 `audit_sample(rate_override=1.0)` → `{audited: 2, failed: 1, E: 0.5}`，
  下一轮只重读被改的那个（`raw=1 placeholder=1`）。**自测已覆盖（第 11 条）。**

## 3. 然后算了一笔账，发现它和门重复了

世界第 0 轮漂移，问"第几轮被发现"（5000 次模拟）：

| 机制 | 参数 | 平均检出轮 | 最坏 |
|---|---|---|---|
| 指纹门 | interval=1 | 1.0 | 1 |
| 指纹门 | interval=5 | 5.0 | 5 |
| 静态抽检 | rate=3% | **33.1** | 323 |
| 静态抽检 | rate=10% | 9.9 | 89 |
| 静态抽检 | rate=25% | 3.9 | 32 |

**结论与直觉相反**：静态抽检检出"世界变了"**远慢于**指纹门。
要追上 interval=5，抽样率得 ≥20%——那时成本已不划算。

分工必须写清楚：

- **世界指纹**：负责"世界变了"（确定性、批量、便宜）
- **抽检**：只对**动态验证器**（跑测试/类型检查）有意义，它能发现"当初就推错了"
- **静态抽检在 v0.1 里只是占位实现，不是防错主力**

## 4. 一条方法教训（比结论更值钱）

第一次写这个模拟时，本鱼把"每轮对 62 条记忆各抽一次"实现成了"漂移条目每轮有 62 次机会"，
得出"抽检 1.2 轮就能检出、比门还快"的**反向结论**。

> **模拟写错比不写更危险，因为它看起来像数据。**

已把这条写进 design.md 同一节作为警示。

# 同日第十五轮：动态抽检落地 —— "可验证优先"终于有了可执行版本

## 1. 本轮补的是什么

上一轮承认：静态抽检和指纹门重复，且发现不了"当初推错了"。本轮把它补上：

- `Memory` 增加 `claim`（自然语言结论）+ `verifier`（可执行校验器）
- `Runtime.remember(cid, claim, verifier)`：把结论和"怎么验证它"一起固化
- `Runtime._run_verifier()`：subprocess 执行，`returncode == 0` 视为仍成立，超时 30s
- `_verify_one` 优先用校验器（动态），没有则退回符号哈希（静态）
- 账本记录 `dynamic:cmd` / `static:symbol_hash`，E 的来源可追

## 2. 实测（`experiments/m5_verify.py`）

2 条结论：`add(1,1)==2`（对）、`is_adult(20) is False`（故意写错）。

```
抽检 2 条，判错 1 条，E=0.500，耗时 68ms（每条约 34ms）
  [fresh] add(1,1)==2
  [stale] is_adult(20) is False（错误结论）   verifier=cmd
```

**错的被抓、对的没被误伤、成本 34ms/条。** 这是静态哈希做不到的事：
代码一个字没改，但结论本身是错的。

## 3. 边界（必须一起读）

只有**写得出可执行校验器**的结论才能被动态验证。
"这个方案更好""用户想要更短的回复"这类写不出来的，仍然只能静态校验 —— 而静态永远发现不了推错。

所以"能被验证的才配被记住"不是口号，是这套系统里一条**会直接决定 E 的上限**的判据。

# 同日第十六轮：结论层进入装配 —— 以及一次被数据打掉的直觉

## 1. 做了什么

`assemble` 现在按信任度择优输出：
- primary 命中 + 已固化 + **有 claim** → 输出「已验证结论」块
- 否则 primary 命中 → 摘要卡
- 否则 → 占位符 / 未加载占位符

也就是说：**能直接给结论的时候，不再给代码让模型重推。**

## 2. 本鱼的直觉被打了

我原以为"结论比卡片更省 token"。实测（`m6_claims.py`）：

| 符号 | raw | card | claim | 谁最便宜 |
|---|---|---|---|---|
| tiny（1 行函数） | **17** | 32 | 24 | **raw** |
| bulky（~30 行） | 257 | **57** | 68 | **card** |

两条反直觉结论：
1. **短符号上原文最便宜**——claim 的固定开销付不起；
2. **长符号上卡片反而比结论便宜**——claim 的长度取决于结论写得多啰嗦。

## 3. 那 claim 到底值什么（修正后的表述）

> **card/raw 省的是「字」，claim 省的是「想」。**

模型拿到 claim 就能直接采用，不用从 257 token 的代码里重新推导出"它会抛什么异常、返回什么"。
省的是**推理**，不是 token。这一点写进了论文方法节与讨论节。

## 4. 边界

- claim 只覆盖写入时断言过的内容；断言之外仍需 card/raw/recall
- claim 谁写、写错了怎么办 → 依赖动态抽检（上一轮）+ 人工
- claim 本身可能过时 → 由 guard + 抽检兜底

## 5. 现状

- 12 条自测全绿；`reproduce.py` 正常
- 新增 `experiments/m6_claims.py`
- 机制清单第 8 项（结论层）现在有代码、有测试、有数据、有边界说明

# 同日第十七轮：多随机种子 —— 顺手发现一个必须自曝的硬伤

## 1. 为什么做这个

前面所有实验只跑了 seed=7。审稿人第一句话就是"只报一个 seed？"。
本轮跑 5 个 seed（7/11/13/17/19），结果写进 `experiments/SEEDS.md`，全部列出，不挑最好的。

## 2. 结果（均值 ± 总体标准差，n=5）

| 方法 | C_cum | R_prompt | R_avail | 总 token |
|---|---|---|---|---|
| full | 0.000 | 0.718 ± 0.045 | 0.718 | 305,768 |
| window-5 | 0.776 ± 0.020 | 0.559 ± 0.039 | 0.559 | 68,486 |
| summary | 0.855 ± 0.010 | 0.542 ± 0.037 | 0.542 | 44,058 |
| grep-RAG | 0.858 ± 0.011 | **0.703 ± 0.054** | 0.703 | 43,195 |
| **ctxfold** | **0.925 ± 0.008** | 0.633 ± 0.030 | **1.000 ± 0.000** | **22,774** |

逐 seed 对照：R_prompt 上 ours **4/5 个 seed 低于** grep-RAG（只有 seed=19 反超，因为 rag 那次 0.605 偏低）。
成本低 47%，方差更小（0.030 vs 0.054，说明我们的结果更稳定）。

## 3. 发现的硬伤：R_avail ≡ 1.000

5 个 seed 全部正好 1.000、方差为零。查清楚原因后结论很难看：

> gold = {本轮符号} ∪ {它的 1 跳依赖}；闭包按**同一张依赖图**展开，查询又必然命中本轮符号。
> 于是 gold ⊆ 闭包**恒成立**，闭包里没给原文的项又都会变成可 recall 占位符 ⇒ R_avail 必然 = 1.000。

**这不是性能，是定义的必然。** 前几轮我拿它当卖点说"可召回证据率满分"，属于自我欺骗——
和"用 gold 来自证 gold"是同一个错误。

处理：在 README、SEEDS.md、论文方法节与威胁节**同时标注这是自证结构，禁止当主要卖点**。
有信息量的只剩两条：R_prompt（0.633，4/5 seed 低于 rag）与 token 成本（-47%）。

## 4. 这条教训的普适形式

> **一个指标如果在你的构造下恒等于极值，它就没有测量任何东西。**

以后任何"看起来完美"的数，先问一句：它是测出来的，还是我自己的定义造出来的？
（这已经是同一天里第二次抓到这类问题了：上一轮是"自动生成文案里藏着等成本"。）

## 5. 现状

- 新增 `experiments/SEEDS.md`（5 seed 全量 + 自曝说明）

# 同日第十九轮：消融 —— 找到一个真正的产品旋钮，和一个指标盲区

## 1. 结果（同一任务序列，50 轮，seed=7）

| 配置 | 总 token | 相对 base | R_prompt | R_avail | 长程引用 R |
|---|---|---|---|---|---|
| base | 22,114 | 1.00× | 0.626 | 1.000 | 0.429 |
| −closure | 13,824 | 0.63× | 0.561 | 0.705 | 0.327 |
| **−placeholder** | 31,114 | 1.41× | **0.939** | 1.000 | **0.850** |
| −card | 20,986 | 0.95× | 0.626 | 1.000 | 0.429 |
| −claim | 22,114 | 1.00× | 0.626 | 1.000 | 0.429 |
| +full | 271,982 | 12.30× | 0.717 | 0.717 | 0.751 |

## 2. 三条结论

1. **闭包是性价比之王**：关掉它省 37% token，可召回率从 1.000 掉到 0.705。
   换句话说，我们全部的"可得性"优势几乎都来自闭包这一个部件。
2. **占位符是一个真正的产品旋钮**：关掉它（已固化也重发原文）多花 41% token，
   换回 **31 个点**的严格可见率，长程引用从 0.429 跳到 0.850。
   ⇒ 应该把它做成显式配置 `strict_visibility`：改代码/审查场景开，闲聊场景关。
   这是本轮唯一"可以直接写进 README 的配置建议"。
3. **card / claim 在过程指标下完全不可见**（对 R 无影响，card 反而多花 5% token）。

## 3. 第 3 条其实是坏消息，必须写在论文里

我们的全套过程指标（C / R_prompt / R_avail / H / E）**只认原文**。
卡片和结论这两个"表示层"部件，无论好坏，指标都看不见。

这意味着：
- 前几轮用 R 系列指标论证"摘要卡/结论层有用"，**在方法论上是不成立的**；
- 它们的价值只能由在线 A 衡量（而在线实验缺凭据）。

已写进论文 §7 威胁第 11 条，以及 RQ6 的第 3 条结论。
**这是本文最重要的一条自我批评。**

# 同日第二十轮：把旋钮做成配置 + 吃自己的狗粮

## 1. `strict_visibility` 落地

消融发现的旋钮（RQ6 结论 2）做成了真配置：

```bash
python -m ctxfold.cli --corpus REPO --state .ctxfold --strict ask "..."
```

- `Runtime(strict_visibility=True)` → 已固化内容也重发原文，不走占位符
- CLI `--strict` 已通
- 自测第 13 条：strict 下必须重发原文且不出现占位符

实测（玩具仓库）：非 strict 第 2 轮 26 token（卡片+占位符），strict 第 2 轮 13 token（原文）。
**短函数上 strict 反而更便宜**——与 m6 的交叉点结论一致。

## 2. 吃自己的狗粮（以 `src/` 为语料，30 轮）

| 方法 | 总 token | C_cum | R_prompt | 长程引用 R |
|---|---|---|---|---|
| full | 84,239 | 0 | 0.711 | 0.817 |
| summary | 17,727 | 0.790 | 0.497 | 0.317 |
| grep-RAG | 27,777 | 0.670 | **0.661** | **0.633** |
| **ctxfold** | **9,962**（全量 recall 19,328） | **0.882** | 0.472 | 0.183 |

三条观察：

1. **成本优势复现**：省 88%（相对全量），比 grep-RAG 便宜 64%；
2. **严格可见率劣势也复现，而且更大**：0.472 vs 0.661（−19 点），而在 stdlib 上是 −7 点。
   原因：本仓库模块互相引用密集（assembler↔runtime↔chunker），依赖多 → 更多项被降级成占位符。
3. **长程引用更差**：0.183 vs 0.633。同样是"依赖密集"的直接后果。

## 3. 这条跨语料结果的价值

在第二个语料（而且是"不同种类"的语料：自家工程代码而非 stdlib）上，**方向完全复现、幅度不同**。

对论文来说这正是需要的：不是"在某个语料上碰巧成立"，而是"机制导致的系统性权衡，
其幅度取决于代码的依赖密度"。已写进 README 与笔记。

## 4. 顺带确认的一个事实

**依赖密度决定了这套方法的收益结构**：
- 依赖稀疏（stdlib 单文件函数为主）→ 严格可见率损失小（−7 点）
- 依赖密集（自家工程，模块互相调用）→ 严格可见率损失大（−19 点）、长程引用更差

这给了一条可测的适用边界：**先用 AST 统计仓库的平均出度，再决定要不要用这套东西。**
（下一步可以把这个判断做成 `ctxfold doctor` 命令。）

# 同日第二十一轮：`ctxfold doctor` —— 把适用边界变成可执行判断

## 1. 做了什么

新增 `src/ctxfold/doctor.py` + CLI 子命令：

```bash
python -m ctxfold.cli --corpus REPO --state .ctxfold doctor
```

输出：规模/粒度、依赖结构（平均出度、跨文件边占比、孤立符号占比）、
模拟 20 轮的「全量 vs 默认 vs --strict」对比，以及**建议预算**与**是否开 strict**。

判断依据刻意用**模拟出来的真实损失**，而不是出度这类代理指标——
因为实测证明代理会骗人（见下）。

## 2. 两个语料的体检结果（方向相反，且与实测一致）

| | stdlib/http | 本项目 src |
|---|---|---|
| 跨文件边占比 | 5.5% | **45.7%** |
| 平均出度 | 0.98 | 1.09 |
| 默认配置 严格可见率 | 0.824 | **0.463** |
| --strict 严格可见率 | 0.968 | 1.000 |
| 严格可见率损失 | 14% | **54%** |
| 建议 | 默认即可 | **开 --strict** |

**关键教训**：出度几乎一样（0.98 vs 1.09），但严格可见率差了一倍。
如果用"平均出度 ≥1.5 就判密集"的规则，两个仓库都会被判成"中等"——**代理指标在这里完全失灵**。
所以 doctor 直接用模拟损失判定：`loss = strict_r - loose_r`，≥25% 就建议开 strict。

## 3. 两个被自己抓到的 bug

1. **verdict 用错指标**：第一版用 avg_out_degree 判定，把 src（损失 54%）判成"中等"。
2. **loss 符号写反**：`loose_r - strict_r` 得到负数，于是打印"损失很小（-54%）"。

两个都不是崩溃，而是**结论错误**——比崩溃更危险。
被自测里"必须同时给出建议且值域合法"的断言挡不住，是靠**人眼看输出**抓到的。
→ 记一条：**自动化测试能防崩溃，防不住胡说；关键输出必须人人眼过一次。**

- CLI 六个子命令：init / ask / status / audit / doctor

# 同日第二十二轮：selfcheck —— 一个防自己的脚本

1. **把默认 tokenizer 改回估算器**（零依赖、跨环境确定），精确值用 `CTXFOLD_TOKENIZER=exact` 显式开启；

| 语料 | 中位相对误差 | p10 | p90 |
|---|---|---|---|
| Lib/http | **+30.0%** | +5.1% | +48.8% |
| ctxfold/src | 0.0% | −25.4% | +16.9% |

**方法上（更重要）**：文档里写了半年的"±15%"从未被验证过，一测是 +30%。

## 顺手抓到并修掉一个显示缺陷

小仓库（3 个符号）上 doctor 打印「省 **-120%**」——负数节省，用户会以为自己算错了。
改为两种说法：
- 正数：`省 79%`
- 负数：`不划算（多 120%）`（并说明小仓库上闭包+出处头可能比单轮全量更贵）
另外在 `chunks < 20 或 模拟轮数 < 5` 时加一行：
`⚠ 仓库过小（3 个符号 / 模拟 1 轮）：本诊断不稳定，仅供参考。`

Lib/http 复核：`省 79%`、严格可见率 0.824 → 结论仍是"中等损失，先用默认配置"。
