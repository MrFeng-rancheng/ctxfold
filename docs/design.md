# 设计：有状态推理运行时

## 0. 问题定性

现有代码 Agent 的推理是**无状态重演**（stateless replay）：每一轮把全部历史重新送进模型，靠重读回忆、靠重推确认。
代价结构：每步开销 ∝ 全部历史长度，因此延迟与账单随会话轮数增长。

ctxfold 的目标形态是**有状态推理**（stateful reasoning）：维护一个显式状态，每一步只对"未决且被依赖"的部分计算。

类比来源（同一数学结构的不同领域实例）：memoization、编译器的公共子表达式消除、数据库物化视图、电子表格的脏格重算。

## 1. 与 KV cache / prompt cache 的本质区别

| | KV cache | ctxfold |
|---|---|---|
| 缓存对象 | 某段 token 序列的中间张量 | 某条结论及其成立前提 |
| 命中条件 | 输入逐字相同 | 前提在相关维度上一致 |
| 换个说法 | 全 miss | 可命中 |
| 前提变化 | 不可感知 | 精确失效 |
| 实现位置 | 必须改推理引擎 | 纯 API/文本层，模型无关 |

一句话：**KV cache 缓存"字"，ctxfold 缓存"理"。**

## 2. 数据模型（v0.1 草案）

```jsonc
{
  "id": "N0042",
  "kind": "fact",                  // constant | fact | preference
  "claim": "retry 逻辑在 order.py L88-102，最多重试 5 次",
  "evidence": [{"path": "src/order.py", "span": [88, 102], "sha256": "..."}],
  "guard": {                        // 必须机器可判定
    "type": "file_hash",
    "path": "src/order.py",
    "sha256": "a1b2..."
  },
  "trust": "T1",                    // T0 | T1 | T2 | T3
  "status": "fresh",                // fresh | stale | suspect
  "deps": ["N0031"],                // 我依赖谁
  "used_by": ["N0050"],             // 谁依赖我（失效传播用）
  "created_at": "2026-11-12T19:40:00+08:00",
  "verified_by": "static:hash"      // static:hash | dynamic:test | none
}
```

## 3. 三类记忆与各自的生命周期

| 类 | 例 | guard | 允许的最高信任档 |
|---|---|---|---|
| constant 契约/常量 | 函数签名、`data.items` 字段、依赖版本 | 文件 hash + 符号表 | T0 |
| fact 版本化事实 | "L88-102 是 retry 循环"、"成因是空 id 未校验" | git HEAD + 工作区脏文件 hash | T1 |
| preference 任务态/偏好 | "本次是重构不是加功能" | 任务 ID + 用户原话指针 + TTL | T2 |

## 4. 四级信任

| 档 | 条件 | 行为 |
|---|---|---|
| T0 免检 | guard 可机械验证且通过 | 直接用，零计算 |
| T1 留痕 | 有证据指针 | 用，但输出必须带 `[#id]` 引用 |
| T2 复核 | 半可判定（偏好/约定） | 用前做一次低成本 verify |
| T3 重算 | 不可判定 / 高时效 / 高风险 | 永不固化 |

**越难判定的前提，复用等级越低。** 这是"省"与"稳"的技术形态，也是可调旋钮。

## 5. 世界指纹（repo fingerprint）

```
fingerprint(scope) = sha256(
    sorted(依赖文件内容的 sha256)
  + git HEAD
  + lock 文件版本
  + 日期（可选，用于 TTL 类）
)
```

指纹变化 → 该 scope 内 T0/T1 记忆**批量标记 stale（标记，非删除）**。
多数错误不是推理错，而是世界变了；这一层以近乎零成本挡掉其中的大部分。

## 6. 失效：降级而非删除

```
前提变 → 结论标 stale（保留）
      → 沿 used_by 标记下游为 suspect
用到时才处理 → 先 cheap check → 通过则复活；不通过则重算，新旧并列
新旧冲突 → 不投票、不猜，回到原文证据仲裁
```

好处：不雪崩（大部分下游其实未受影响），可回退（旧结论仍在，可对比"当初为何如此判断"）。

## 7. 三级验证器（代码域红利）

1. **静态**（0 成本、毫秒、100% 可靠）：文件 hash、符号存在性、签名匹配、import 图、grep 命中
2. **动态**（秒级，一经验证可升 T0）：单元测试、mypy/pyright、ruff、repro 脚本
3. **外部状态**（0 成本）：git log/blame、CI 状态、lock 文件

## 8. 可验证优先（设计第一性判据）

**能被外部验证的结论才配被记住。**

| 结论 | 可外部验证 | 缓存优先级 |
|---|---|---|
| 函数返回 `data.items` | 跑一次即知 | 最高 |
| 该 SQL 会超时 | 执行即知 | 高 |
| 此处有 off-by-one | 写测试即知 | 高 |
| 用户想要更短回复 | 仅靠反馈 | 中 + TTL |
| 这个方案更好 | 不可验证 | 永不固化 |

## 9. 抽检（唯一能发现"固化错误"的机制）

- 以比例 p（默认 3%）随机让已固化结论重新验证，比对结果
- 分歧率上升 → 该类整体信任下调（T1→T2→T3）
- 成本 = 额外 p 的 token，换一张错误率体检表；p 与 E、C 的关系是论文的一张主图

## 9.5 抽检 vs 世界指纹：谁负责什么（时延分析）

世界第 0 轮漂移，问"第几轮被发现"（5000 次模拟）：

| 机制 | 参数 | 平均检出轮 | 最坏 |
|---|---|---|---|
| 世界指纹门 | interval=1 | 1.0 | 1 |
| 世界指纹门 | interval=5 | 5.0 | 5 |
| 静态抽检 | rate=3% | **33.1** | 323 |
| 静态抽检 | rate=10% | 9.9 | 89 |
| 静态抽检 | rate=25% | 3.9 | 32 |

**结论（与直觉相反）**：静态抽检对"世界变了"的检出**远慢于**指纹门，因为它每次只看一个概率。
要追上 interval=5 的门，抽样率得 ≥20%，而那时成本已经不划算。

因此二者的分工必须写清楚：
- **世界指纹**：负责"世界变了"（确定性、批量、便宜）；
- **抽检**：只对**动态验证器**（跑测试/类型检查）有意义——它能发现"当初就推错了"，
  而这是指纹永远发现不了的。**静态抽检在 v0.1 里只是占位实现，不应被当成防错主力。**

**动态验证的落地（v0.1 已实现）**：`Runtime.remember(cid, claim, verifier)`，
`verifier = {"kind": "cmd", "cmd": [...]}`。抽中即执行，`returncode == 0` 视为结论仍成立。
实测（`experiments/m5_verify.py`）：2 条结论中 1 条故意写错 → E = 0.5，错的被标 stale、对的保持 fresh，
每次校验约 34ms。

**它的边界就是"可验证优先"原则本身**：写得出可执行校验器的结论才能被动态验证；
写不出的（"这个方案更好"）只能退回静态哈希，而静态永远发现不了"推错了"。
这也解释了为什么"能被验证的才配被记住"是一条设计判据，而不是一句漂亮话。

（记一条方法教训：本文第一次写的时延模拟把"每轮抽 62 次"算成了"漂移条目每轮 62 次机会"，
得出"抽检更快"的反向结论。**模拟写错比不写更危险，因为它看起来像数据。**）

## 10. 一个回合的走查（第 37 轮，50 轮修 bug 中段）

问："为什么 `processOrder` 里那个 retry 会死循环？"

1. 解析实体：`processOrder`、`retry`
2. 查状态：命中 `#N0042`（T1，guard=file hash `a1b2`）
3. 验 guard：hash 不匹配（`a1b2`→`c3d4`）→ `#N0042` 标 stale，下游标 suspect
4. 局部重算：仅读 `order.py` L80-115（≈300 token），而非全量历史（≈120k）
5. commit 新结论 + 证据指针 + 新 guard
6. 输出带 `[#N0051]` 引用，可点开看原文
7. 抽检命中（3%）→ 顺手跑相关测试验证

## 11. 已知失败模式（必须监控）

- **未决判定错误**：该算的没算（漏）/ 不该算的反复算（原地循环）
- **进展度量缺失**：状态机无限打转，烧 token 而"自以为在深思" → v0.1 必须内置进展度量 + 循环检测
- **语义等价不可判定**：`1+1` / `一加一` / `2-1+1` 无法机械判同 → 会有漏命中（只少省钱，不出错）与误命中（会出错）
- **误命中代价**：宁可漏省，不可错省。默认偏保守。
