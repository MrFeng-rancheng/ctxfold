# 把上下文从「重演」变成「状态」：面向代码 Agent 的增量上下文装配

**（草稿 v0.3 ／ 行文修订版 ／ 数字全部来自 [附录 A](appendix-experiments.md)）**

---

## 摘要

多轮代码 Agent 的推理本质上是一种**无状态重演**：模型唯一的记忆载体是文本，于是「回忆」只能靠重读历史，
「确认」只能靠重新推导。其代价结构使第 t 轮的开销正比于全部历史长度——本文在 50 轮会话上实测，
单轮提示由 659 token 增长至 9,693–14,010 token。

本文提出 ctxfold：把上下文由「线性文本」改造为「带守卫条件的结论状态」。
每条结论在通过机器可验证的检查后固化，并携带可被程序判定的守卫条件、证据指针与依赖边；
前提不变时以卡片或已验证结论的形式廉价复用，前提变化时沿依赖图精确失效、只重算受污染的子图。
在 Python 标准库语料、5 个随机种子上，ctxfold 将累计输入 token 降至全量基线的 7.9%
（305,768 → 24,282），相对最强基线（BM25 检索）降低 47%，且种子间方差更小。
代价是把「当场可见」换成「按需取回」：严格可见证据率由 0.703 降至 0.633。

我们同时给出三项过程指标（证据保留率、免算率、错误残留率），并诚实标注其中一项的失效：
在本任务构造下，可召回证据率恒为 1.000，属定义的必然，不构成测量。
本文的核心主张与其反驳条件一并给出；真实模型上的正确率与免算率尚未测量，这是本文的主要缺口。

## 1. 引言

### 1.1 问题的形状

大语言模型在长程任务中没有「状态」，只有「文本」。这一事实的后果常被低估：
模型无法「记得」，只能「重读」；无法「确认」，只能「重推」。
每次交互，它都要把此前的全部历史重新编码一遍，并以同样的算力重新得出此前已得出的结论。

这一代价是可以被结构化的。人类不会为回答一加一而重新演算：算过的结论被折叠成「已知」，
此后以查表成本复用。计算机科学对此有四组同构的先例——函数记忆化、编译器的公共子表达式消除、
数据库的物化视图，以及电子表格的脏格重算。它们的共同点不是「压得更小」，
而是**把一次计算沉淀为一个免于重算的对象，并在其前提变化时精确地撤销它**。

本文要问的是：能否把这一结构引入代码 Agent 的上下文管理，使算力只花在「未决」之处？

### 1.2 与缓存工作的关键区别

工业界的 prompt cache 与 KV cache 常被误认为已经解决了上述问题，但二者缓存的不是同一种东西。
KV cache 缓存某段 token 序列的中间张量，命中要求输入**逐字相同**；一旦换一种说法或改动前缀即失效，
且它无法回答「这条结论的前提是否仍然成立」。本文缓存的是**结论及其成立前提**，
命中要求前提在相关维度上一致，且前提变化时可被精确撤销。

一句话概括这一区别：**KV cache 缓存「字」，本文缓存「理」。**

它同时决定了实现位置：前者必须改动推理引擎，后者可完全工作在应用层，
因而与模型无关——只产生标准的 messages，交给任意客户端发送即可。

### 1.3 本文的主张

本文只主张一个可被反驳的命题：

> 在代码 Agent 的多轮会话中，把上下文从「重演历史」改为「维护带守卫的结论状态」，
> 可以在不降低证据可得性的前提下把输入 token 降低 47%–93%；
> 代价是把「当场可见」换成「按需取回」，因此收益与模型主动取回（recall）的倾向强相关。

该命题的反驳条件全部可测，见表 1。我们把它写进正文而非局限一节，
因为**一个无法被反驳的命题不是命题**——这也解释了为何本文不采用「分层架构、逐层优化」的叙述：
那种叙述既不可测，也不可证伪。

**表 1　命题的反驳条件**

| 反驳条件 | 若成立意味着 |
|---|---|
| 模型几乎不 recall，且任务以语义类为主 | 收益归零，甚至不如全量（§5-RQ5） |
| 结论状态频繁失效（世界变化快） | 重算开销吃掉节省（§5-RQ3） |
| 依赖闭包覆盖不到所需证据 | 可得性下降（本文严格可见率已低 7 个百分点） |
| 装配与自校验开销超过节省 | 净收益为负（世界指纹在 2000+ 文件仓库上 261 ms/轮） |

我们不主张：模型因此更聪明、准确率提升、可以替代 KV 缓存或检索、在短对话中有收益，
以及——尤其重要地——不主张「可召回证据率 = 1.000」是一种性能（那是定义，见 §5 之 RQ2）。

### 1.4 贡献

其一，给出**结论状态的数据结构与增量求值语义**：结论、守卫、依赖、信任档与可执行校验器构成五元组，
并定义其失效传播规则。其二，提出**可逆降载**：被移出上下文的内容以「可按需取回的表示」保留，
与有损摘要形成机制上的对照。其三，提出并检验**三项过程指标**，
把「压缩是否安全」从单点准确率拆成可测量的机制量，同时公开其中一项在本任务构造下的失效。
其四，**量化防错体系**：符号级守卫相对文件级把误失效由 20 条降至 3 条，
选择性重算相对全量失效节省 87.5%–95.0%。其五，报告**负面结果与效度威胁**，
包括严格可见率低于检索基线、世界指纹的自身开销、静态抽检的时延劣势，
以及过程指标对「表示层」的盲区。

## 2. 形式化

设会话状态为 `S = ⟨C, G, D, L⟩`，其中 `C` 为结论集、`G` 为守卫集、`D` 为依赖图、`L` 为账本；
一条结论写作 `c = ⟨claim, evidence, guard, deps, trust, verifier⟩`。

**守卫的可判定性**是本文的第一条设计约束：`guard` 必须是可被程序求值的谓词，
例如文件或符号的哈希、版本号、符号存在性，或一条可执行的检查命令。
无法机械判定的前提不得固化（信任档 T3，每轮重算）。这条约束的意义不在于「更严格」，
而在于**把「是否可安全复用」从模型的自我判断中移出**——后者是 2026 年若干学习式驱逐工作的共同失败点。

给定查询 `q`，装配集合为 `A(q) = Closure(Hits(q), h)`，其中 `Hits` 为符号级匹配，
`Closure` 沿依赖边展开 `h` 跳（默认 1 跳；2 跳的消融见 §5 之 RQ3）。

**可逆降载**要求 `A(q)` 中每个元素要么以原文出现，要么以「可按 id 取回原文」的表示出现
（结论块、摘要卡、占位符）。该不变量使「移出上下文」成为可逆操作，
从机制上区别于摘要式压缩——后者丢弃的信息不可恢复。

**增量求值**：当世界指纹变化时，失效集定义为 `I = {c : guard(c) 不再成立} ∪ Downstream(I)`，
仅对 `I` 重算。选择传播而非全量失效的代价是：若依赖图不完整，污染可能被低估，见 §7。

## 3. 方法

### 3.1 四层表示

同一份内容在本文中有四种表示，按信息密度与成本排序，装配时择优。
**原文**信息最全而成本最高。**已验证结论**直接给出可采用的结果；
但实测表明它并不比原文或卡片更省 token（1 行函数：原文 17、卡片 32、结论 24；
30 行函数：原文 257、卡片 57、结论 68）——其价值在于**省去一次推理**而非省去若干 token，
即「卡片与原文省的是字，结论省的是想」。**摘要卡**形如 `#id | path:lines | 签名 | calls`，
约 20–40 token，可独立回答「在哪、调用了谁」。**占位符**仅含 id，需要时按 id 取回原文。

四者的选择不是静态配置，而由本轮命中决定：被点名且已固化的符号优先给结论或卡片，
未被点名的依赖给占位符，超出预算的项降级为「未加载占位符」而非丢弃——
丢弃会使证据连「可取回」都失去；该修正使 gold 中彻底缺失的比例由 20.2% 降至 15.1%。

### 3.2 三个防错机制

**符号级守卫。** 每条结论绑定其符号文本的哈希，而非整个文件的哈希。理由是可测的：
文件级守卫会把同文件内无关函数的改动一并视为失效。在 62 条记忆、修改 3 个符号的设置下，
文件级失效 20 条而符号级失效 3 条，误失效占记忆的 70.8%，重算成本高 3.1 倍。
符号级的失效集在结构上恒为文件级的子集，但节省幅度取决于改动落在多大的文件里，
故本文不宣传固定倍数。

**世界指纹。** 每轮以廉价指纹（路径、大小、mtime）判断世界是否改变，未变则跳过全库重读，
变了再做逐文件校验。该门只用于跳过，不用于判定失效：误报的代价是多读一次盘，
漏报的代价是使用错误结论。实测显示它自身也是成本项——2,213 个文件上每轮 261 ms，
超过装配开销两个数量级，因此必须按间隔节流，代价是存在最多 N 轮的失效窗口。

**抽检与账本。** 所有提交、失效、复用与审计写入 append-only 账本，可回放任意时刻状态并截断回退。
抽检分静态（哈希比对）与动态（执行结论自带的校验器）两级。
实测显示静态抽检对「世界改变」的检出显著慢于世界指纹门（3% 抽样下平均 33.1 轮对应 5 轮），
故其定位不是防错主力；能发现「代码未变而当初推错」的是动态校验——
我们验证了这一点：两条结论中故意写错一条，动态抽检给出错误残留率 0.5，
错误者被标记失效、正确者保持有效。

## 4. 指标

本文报告六项指标，前四项不依赖模型，因而完全可离线复现（表 2）。

**表 2　指标定义**

| 指标 | 定义 | 依赖模型 |
|---|---|---|
| C | 1 − 装配 token / 全量 token | 否 |
| R_prompt | gold 中「原文确在提示内」的比例（模型从不 recall 的最坏情况） | 否 |
| R_avail | gold 中「在提示内或可 recall」的比例 | 否 |
| H | 无需 recall 即答对的回合比例 | 是 |
| E | 抽检判错数 / 抽检数 | 部分 |
| L | 每轮端到端时延（p50/p95） | 是 |

须特别声明：`R_avail` 在本任务构造下恒为 1.000——gold 由依赖图生成，闭包按同一张图展开，
故 gold ⊆ 闭包必然成立，而闭包内未给原文的项又都会成为可 recall 的占位符。
这一数字不测量任何内容，本文仅将其作为定义性注记保留，不作性能主张。

## 5. 实验与结果

设置、语料、种子与全部原始结果见 [附录 A](appendix-experiments.md)。以下按六个研究问题组织。

### RQ1 节省了多少

在 5 个随机种子、50 轮、含 40% 长程引用的合成会话上（表 3），ctxfold 的累计输入 token
为全量基线的 7.9%，相对最强基线降低约 44%，且种子间方差更小（0.030 对 0.054）。

**表 3　五种上下文策略（均值 ± 标准差，n = 5）**

| 方法 | C_cum | R_prompt | 总 token |
|---|---|---|---|
| full（全量） | 0.000 | 0.718 ± 0.045 | 305,768 |
| window-5 | 0.776 ± 0.020 | 0.559 ± 0.039 | 68,486 |
| summary（抽取式） | 0.855 ± 0.010 | 0.542 ± 0.037 | 44,058 |
| grep-RAG（BM25） | 0.858 ± 0.011 | **0.703 ± 0.054** | 43,195 |
| **ctxfold** | **0.920 ± 0.008** | 0.633 ± 0.030 | **24,282** |

### RQ2 代价是什么

代价是严格可见证据率下降约 7 个百分点：已知证据被替换为卡片或占位符，其原文需一次取回才能进入提示；
该差异在 5 个种子中的 4 个成立。此外，长程引用场景下本文的严格可见率为 0.429 而 BM25 为 0.731，
原因朴素而重要：**BM25 直接在全部代码中检索，本就不依赖「记住」**。
换言之，「长程记忆」并非本文独占的解法，检索是它的廉价替代。
本文与检索的真正差异在于成本结构（已知内容不重复付费）与增量性（前提变化时知道该重算什么），
而不在于「证据更多」。

### RQ3 防错机制是否值得

符号级守卫把误失效由 20 条降至 3 条（记忆的 70.8%，重算成本 3.1 倍）；
失效沿依赖传播时，只重算受影响项及其下游相对全量失效节省 87.5%–95.0%。
两项收益都依赖一个前提：依赖图足够完整。本文的图为 1 跳、含跨文件 import 边，
在标准库上 316 条依赖中 17 条跨文件；真实工程更密，传播成本必然上升。
作为负结果，扩展到 2 跳使严格可见率由 0.498 降至 0.407、成本上升 10%，故默认取 1 跳。

### RQ4 机制自身的开销

世界指纹在 2,213 个文件上每轮 261 ms，必须节流（§3.2）。静态抽检的检出时延为 33.1 轮（3% 抽样），
远慢于间隔 5 轮的指纹门，故不作为主力。等精度方向上，检索基线即便把预算放大到 19,200
（261,451 token）证据率也封顶于 0.802；但如 §7 所述，该结论受 gold 同源问题影响，
本文不将其作为独立证据。

### RQ5 真实模型下的表现（deepseek-chat，90 次调用）

首次在线实验（`experiments/runs/20261112-212240-m3-real`，30 符号 × 3 题型）：

| 题型 | 结果 |
|---|---|
| 定位（在哪一行） | **30/30 = 1.000** |
| 依赖（调用了谁） | gold 召回率 **0.845**（n=14 非空子集） |
| 语义（抛哪些异常） | **22/30 = 0.733** |
| H（无需 recall 即答对） | **0.322** |
| recall 触发率 | **0.567** |

**复现**：换用 `seed=11` 重跑（同语料 30 符号）：A 0.656、H 0.322、recall 0.567、定位 1.000、语义 0.833；
再换语料（本项目自身 `src/`，10 符号）：A 0.567、H 0.333、recall 0.633、定位 1.000。
三次运行的 H 稳定在 0.32–0.33、recall 在 0.57–0.63、定位题全为 1.000。

**按预注册判据**：recall_rate ≥ 0.5 且语义题 A ≥ 0.5 ⇒ 本文"收益与 recall 倾向强相关"的主张**得到支持**。

**错误残留率 E（模型自写可执行断言）**：给模型代码、让它写一条可执行断言，我们再真跑一遍。
12 个符号下 **E = 0.417**（5 错 / 7 对）。含义是：模型产出的"结论"约四成经不起它自己给出的可执行检查，
**若不经动态校验就固化，状态会被系统性污染**——这正是"可验证优先"判据的实证依据。

**同时必须记录一节课**：首跑时定位题为 0 分，原因不是模型无能，
而是**我们的原文块里没有文件名与行号**——模型无法回答"在哪一行"。
补上 `### #cid | path:start-end` 出处头后，定位题从 0 变为 1.0。
**这个缺陷在全部离线指标里完全不可见**，因为离线只算证据保留率，不问模型能否作答。

## 6. 相关工作

本文与五条线索相邻而着力点不同。KV 缓存驱逐与压缩工作（H2O、SnapKV 一线）在 token 层面缩减缓存；
近期的 PACE 进一步指出「保留并不等于可用」，其障碍来自旋转位置编码造成的距离膨胀——
这与本文互补：它在引擎内解决「取不回」，本文在应用层解决「不必重取」。
长上下文压缩的综述把活跃／非活跃记忆与预算成本模型统一起来，本文可视为其在代码符号上的一个具体实现与指标化。
Agent serving 侧的 MORTIS 与 AKV 把提示组件当作有生命周期的程序变量以复用 KV，
它们复用「文本」，本文复用「结论」。结构化推理方面，GraphEvoResearcher 以成本匹配的消融表明
结构奖励本身并不带来增益，这提醒我们不要主张「图使我们更聪明」，而只主张「图使证据可得性可控」。
自适应计算方向的失败分析（学习式停止门退化为空操作）则支撑了本文的保守选择：
坚持确定性策略，不做学习式路由。

## 7. 效度威胁

按严重程度排列；前两条足以动摇本文结论，故置于最前。

1. **gold 与闭包同源。** gold 由抽象语法树依赖生成，闭包按同一张图展开，故可召回证据率恒为 1.000，
   等精度结论亦含循环论证成分。本文不将其作为独立证据。
2. **E 的测量工具曾三次出错**：模块提示缺包前缀、未设 max_tokens 导致截断、引号被误 strip，
   使 E 从 1.000 依次降到 0.833、0.833、最终 0.417。**每一次下降都不是模型变好，而是尺子修对了。**
   最终 E=0.417 的样本量仅 12，需扩大。
3. **在线结果规模小、单模型、单语料。** 已完成 30 符号 × 3 题型 = 90 次真实调用（deepseek-chat，
   `Lib/http` 语料），结论见 RQ5；但样本量小、未跨模型/跨仓库复现，且依赖题判据在首次运行后
   经过一次修订（见附录 A.14，两次结果均保留）。**更大规模的复现仍是缺口。**
4. **任务是合成的**，由脚本生成，非真实开发者会话。
5. **token 数为估算**（字符数除以 3.5）。实测（附录 A.13）估算器在代码文本上**系统性高估约 30%**，
   故一切绝对 token 数应视为上界；但 C / R 等比值类指标仅差 1.35 个百分点，结论不受实质影响。
6. **严格可见率低于检索基线**（0.633 对 0.703；长程引用 0.429 对 0.731），这是设计代价。
7. **世界指纹存在失效窗口**，节流导致最多 N 轮不校验。
8. **静态抽检检出慢**，不构成有效防线。
9. **收益随题型剧烈变化**，语义类问题在模型不 recall 时为零。
10. **传播精度未测**：污染闭包的过近似率需要语义判断，离线不可得。
11. **2 跳闭包的负结果未在新版切块器上复测**。
12. **过程指标对表示层是盲的**：消融显示卡片与结论块对证据保留率几乎无影响；若其确有价值，本文指标看不见。
    因此本文的离线结果不能用来论证这两个部件——这是对自身方法论最重要的批评。

## 8. 附录与材料

每个数字的来源、设置、复现命令与已知缺陷集中在 [附录 A](appendix-experiments.md)。
其 A.12 节列出本项目在成文前修复的 9 处缺陷：同名符号遮蔽导致 13.7% 的检索指向错误对象、
类整块与嵌套函数造成 46% 的成本虚高、检索预算语义错误、依赖解析的字母序偏置等。
**这 9 处没有一处是程序崩溃，全部是「结论错误」**——这类问题无法由测试捕获，
只能由人审视输出与自检脚本发现。
